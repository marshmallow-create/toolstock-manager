## 1. プロジェクトの目的

工具を「誰が・いつ・どの工具を・何個・どの設備向けに出庫したか」を把握し、在庫数と入出庫履歴を一元管理する。工具ごとに設定した発注点に基づき発注候補を自動生成し、購買担当者の承認を経て発注できる仕組みを構築する。

### 成功条件

1. PCやタブレットで工具を検索し、少ない操作で手動出庫できる。
2. 工具・保管場所ごとの現在庫が正しく表示される。
3. アカウント単位で入出庫履歴が追跡できる。
4. 発注点以下で候補を自動生成し、重複発注を防止できる。
5. 工具管理者・購買担当・一般作業者の権限を分離できる。
6. 最初はローカル開発環境で架空データを使って安全に検証できる。

## 2. 対象と初期スコープ

- 対象工具: 超硬ドリル、エンドミル、旋削チップ、タップ、その他消耗工具。
- 対象組織: まず1工場。将来的に複数工場への拡張を想定するが初期実装は不要。
- 利用端末: Windows PC、タブレット。レスポンシブな日本語Web UI。
- **出庫方式: A — PC・タブレットからの手動登録**。QRコード、バーコード、電子工具棚、センサー連携は初期スコープ外。
- 既存の工具棚を流用する。
- 在庫の単位は工具ごとに「本」「個」などを設定。数量は最小管理単位の整数で保持する。ケース入数は発注単位で別管理。

### 初期スコープ外

- 外部システムへの注文自動送信（メール/API実送信）
- 自動倉庫、電子錠、QRスキャン
- 原価配賦や会計システムとの連携
- 工具寿命・再研磨工程の詳細トラッキング
- 複数工場を横断する在庫移動

### 5.1 手動出庫フロー（重要）

1. ログイン（利用者は自動取得）。
2. 工具番号・名称・型番で工具検索。「最近使った工具」等は後続改善。
3. 工具の保管場所を選択。1か所のみなら自動選択。
4. 出庫数量を入力。初期値1、数量単位を明示し、＋／−操作に対応。
5. 使用設備を選択。前回設備の初期表示は**本人・端末の適切な状態管理**を考慮した後に実装し、初期版では明示選択でもよい。
6. 出庫前の在庫・出庫後見込みを表示。
7. 出庫確定時、**サーバー側で再度在庫確認**し、在庫減算・履歴記録・発注候補判定を行う。
8. 結果を表示し、連打・通信再送で二重出庫させない。

出庫に必要な入力は最小限にする。ただし、設備未選択、数量0以下、在庫超過はエラーとする。未ログインや権限不足の書き込みを拒否する。

## 6. 在庫・発注業務ルール

### 6.1 在庫の定義

- `on_hand`: 実際に保管している数量
- `reserved`: 引当済み数量（初期版で実際の引当操作がない場合は0）
- `available = on_hand - reserved`: 出庫可能数量
- `on_order`: 発注確定済みで未入荷の数量（発注明細から集計する。候補は含まない）
- `inventory_position = on_hand + on_order - reserved`: 発注判定用の在庫ポジション
- `safety_stock`: 安全在庫
- `reorder_point`: 発注点
- `target_stock`: 補充目標在庫

通常は `0 <= safety_stock <= reorder_point <= target_stock` を満たす。発注点は納期中の使用見込みを踏まえて設定する。安全在庫割れは警告を別途表示する。

### 6.2 発注判定

- 工具・発注管理単位ごとに `inventory_position <= reorder_point` なら発注候補を作成・再評価。
- 基本必要数 `max(0, target_stock - inventory_position)`。
- 発注数量は仕入先の発注単位（箱・入数・ロット単位）で切り上げる。
- 既存の未処理候補がある場合は二重作成せず、再計算して更新する。
- 発注承認後の注文残は `on_order` に計上し、同条件の候補が重複発生しないようにする。
- 例：現在庫8、未入荷5、引当2、発注点15、目標20 → 在庫ポジション11、必要9、ロット5なら発注候補10。
- 状態例：`DRAFT` → `PENDING_APPROVAL` → `APPROVED` → `EXPORTED`（発注書出力）→ `ORDERED`（発注確定）→ `PARTIALLY_RECEIVED` → `RECEIVED`。`REJECTED`、`CANCELLED`も考慮。
- **重要：CSV/PDFの生成・ダウンロードは実際に発注先へ送信したことを意味しない。** `ORDERED` への遷移は購買担当が手動で「送付済み／注文確定」を登録する、または将来の連携が成功した場合だけにする。
- 単価、仕入先、発注ロット、納期、発注先型番を注文確定時にスナップショット保存する。
- 部分入荷、取消、返品の整合性を確認する。
- 初期版で外部メール/APIへの実送信は**禁止**。通知もローカル画面内表示のみでよい。

### 6.3 不整合・誤操作防止

- 出庫は「在庫を減らす」と「履歴を残す」を同一DBトランザクションで処理する。
- 同時出庫はPostgreSQLで行ロックまたは条件付き更新を使用し、マイナス在庫を防止する。
- 操作ごとに一意の `idempotency_key`（同一リクエスト再送を一回とみなす識別子）を持たせ、二重処理を防ぐ。
- 履歴を物理削除せず、訂正は理由付きの逆取引で行う。
- 在庫残高を変更できるのは認可されたサーバー処理のみ。
- アプリからの手動SQL更新を許可せず、DBのアクセス権も最小化する。

## 7. DB設計（論理モデル）

### 7.1 基本テーブル

| テーブル | 主要項目 | 備考 |
| --- | --- | --- |
| `users` | `id`, `employee_code`, `name`, `role`, `active`, `created_at` | 社員IDはユニーク |
| `tools` | `id`, `tool_code`, `name`, `category`, `manufacturer`, `model`, `unit`, `active` | 工具番号はユニーク |
| `machines` | `id`, `machine_code`, `name`, `active` | 設備コードはユニーク |
| `locations` | `id`, `location_code`, `name`, `active` | 保管棚・引き出し |
| `stock_balances` | `tool_id`, `location_id`, `on_hand`, `reserved`, `updated_at` | `(tool_id,location_id)` ユニーク |
| `inventory_transactions` | `id`, `tool_id`, `location_id`, `actor_user_id`, `machine_id`, `type`, `quantity`, `idempotency_key`, `reverses_id`, `reason`, `created_at` | 追記型、リクエストIDはユニーク |
| `inventory_policies` | `tool_id`, `location_id?`, `safety_stock`, `reorder_point`, `target_stock` | 初期実装で工具単位か棚単位かを明確に決める |
| `suppliers` | `id`, `supplier_code`, `name`, `email?`, `active` | 仕入先コードはユニーク |
| `supplier_items` | `tool_id`, `supplier_id`, `supplier_model?`, `unit_price`, `order_multiple`, `lead_time_days`, `preferred` | 同一工具に複数仕入先可 |
| `purchase_orders` | `id`, `order_no`, `supplier_id`, `status`, `requested_by`, `approved_by?`, `ordered_at?` | 発注番号はユニーク |
| `purchase_order_items` | `id`, `order_id`, `tool_id`, `ordered_quantity`, `received_quantity`, `unit_price` | 受入数量を追跡 |
| `audit_logs` | `id`, `actor_user_id`, `action`, `entity_type`, `entity_id`, `details`, `created_at` | 重要な操作を監査 |

必要に応じて認証セッション関連、`reorder_candidates`（発注候補）、`goods_receipts`（納品受入と発注ひも付け）のモデルを追加する。発注候補と確定発注は区別する。

### 7.2 推奨制約・インデックス

- 発注数量、在庫数量は**整数**。金額は `Decimal` / PostgreSQL `numeric`。
- `on_hand >= 0`、`reserved >= 0`、`reserved <= on_hand` をDB制約または同等の保証で強制。
- 工具コード、社員コード、設備コード、保管場所コード、発注番号はユニーク。
- 外部キーで参照整合性を保つ。履歴の参照先は原則削除禁止。
- `inventory_transactions` に `(tool_id, created_at)`、`(actor_user_id, created_at)`、`(machine_id, created_at)` の検索用インデックス。
- `purchase_orders` に `(status, created_at)` 等のインデックス。
- DBトランザクションと競合対策を単体・結合テストで検証する。

## 8. 非機能要件

- 画面・エラーメッセージは日本語。
- PC/タブレットに最適化。スマホ表示は可能なら対応。
- サーバー側の入力検証・認証・認可を徹底する。
- SQLインジェクション、CSRF、XSSなどWebアプリの基本対策を行う。
- 監査ログは操作したユーザー、対象、時刻、結果を記録する。
- `.env`、秘密鍵、パスワード、実データはGitに含めない。
- 初期データは架空の社員・工具・設備・仕入先に限定する。
- バックアップと復元の手順を文書化し、本番投入前に復元テストする。
- タイムスタンプはUTCで保存し、画面では日本時間（Asia/Tokyo）で表示。
- 専用サーバーでの運用を見据えるが、**初期はローカル起動のみ**。

### Phase 6 — 運用向け整備

- 履歴CSV、設備別工具費の集計、監査、バックアップ、復元手順、E2Eテスト。
- **完了条件:** 想定利用者による一連の作業テストが通る。

### テストに必ず含めるケース

1. 同じ工具を2人が同時出庫しても負在庫にならない。
2. 同一リクエストIDの再送で出庫が二重計上されない。
3. 発注点以下で候補が作成され、二重候補・重複発注が発生しない。
4. 発注書の出力だけで「発注確定」扱いにならない。
5. 部分入荷と取消で在庫・発注残が整合する。
6. 作業者が管理者権限のAPIへアクセスできない。
7. 訂正後も原履歴と訂正理由が残る。
8. 権限外のマスタ変更や履歴削除が拒否される。
