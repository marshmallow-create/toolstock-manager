# Phase 2 設計

社員ID・パスワードによるローカル認証と、DB保存のランダムセッションを実装する。現在の利用者のPhase 2開始指示を受け、Phase 1限定の作業規約を更新する。

## 選定
Auth.js CredentialsはアカウントのDB永続化やパスワード管理を別途必要とする。外部IDサービスは社内ホスト方針と今回のローカル開発範囲に合わないため採用しない。今回はNode標準scryptとDBセッションを用いた最小構成とする。将来の社内ID連携は別途選定する。

## 構成と保証
- usersに任意のpassword_hashを追加。既存ユーザーは資格情報設定までログイン不可。平文パスワードを保存しない。
- 32バイト乱数のCookieをHttpOnly/SameSite=Lax/Path=/で保持。DBにはSHA-256ハッシュのみ保存。HTTPS時はSecure。
- 30分無操作、最長8時間。認証時にユーザーのactive/roleを毎回DBで確認する。ログアウト・無効化・権限変更・パスワード変更でセッション失効。
- 社員IDごとのDBベース試行制限（15分間に5回まで）、一般化したログインエラー。書き込みでは固定APP_ORIGINとのOrigin照合を必須とする。
- 管理者だけがユーザー一覧・登録・更新へアクセス。自分自身の無効化/降格と最後の有効管理者の喪失を防ぐ。管理変更と監査は同一トランザクション。
- ログイン・マイページ・ユーザー管理を日本語で用意。工具/在庫/発注機能はPhase 3以降。
- 仕様の権限表は共通permissionsモジュールへ集約。権限の隠蔽だけに依存せずページ・API・サービスで認可。
- ローカル初期資格情報は明示コマンドで架空のA001（WORKER）とADMIN001（ADMIN）だけへ設定。ランダムな個別パスワードをGit対象外ファイルへ保存し、既存資格情報を上書きしない。
- ロールは作業者（WORKER）と管理者（ADMIN）の2種類。廃止したロールの既存利用者はWORKERへ移行し、社員ID・パスワード・履歴を維持してセッションを無効化する。昇格は管理者によるユーザー管理から行う。

## 検証
専用DBの一時スキーマへ全DDLを適用。パスワード、全ロールの権限、失効/ログアウト、無効化/権限変更、試行制限、監査と既存履歴の保持を検証。HTTP経由でページリダイレクト・401/403・CSRF・Cookie・管理者操作を検証する。
