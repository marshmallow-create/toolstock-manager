# DB設計

## 履歴の確定値（2026-11-07）

追加移行 `20261107020000_history_snapshots` は inventory_transactions に nullable の on_hand_after（整数）と unit_price（Decimal(14,2)）を追加する。既存行は更新しない。両列は値がある場合に0以上をCHECKし、単価と日時・IDの部分インデックスで範囲検索を補助する。

通常入出庫・取消・工具登録時の初期在庫・初期在庫登録・架空シードは、残高と同じトランザクションで確定値を保存する。取消は元取引の単価（未知ならNULL）を使う。単価の正本は工具単価で、未設定の旧工具だけ既存優先条件を読み取り補完する。既存の履歴保護トリガーを維持する。旧履歴の在庫数は対応する監査記録から読み取り時に補い、価格を現在値から推測しない。

正本: prisma/schema.prisma と prisma/migrations/ 配下の全追加移行。適用済みの初期DDLは変更しない。主キーUUID（Prismaで生成）、時刻timestamptz(3)、金額numeric(14,2)、数量integer。

## モデル

| モデル | 役割 |
| --- | --- |
| users | 社員コード一意、2ロール（WORKER / ADMIN）、無効化。認証資格情報はPhase 2 |
| tools | 工具コード一意、active保持。department・unit_price・shelf_code（棚番）を工具ごとに直接管理 |
| locations | 既存の在庫・履歴の参照先と内部の在庫記録用。利用者向けの管理画面・APIは廃止 |
| machines / suppliers | 旧設備・仕入先の保存専用。既存行と参照は保持し、新規操作・管理APIは廃止 |
| stock_balances | 工具×棚一意、実在庫・引当 |
| inventory_transactions | 符号付き数量。出庫は負数、入庫は正数。操作者必須。新規通常取引のmachine_idはNULL。逆取引は元取引と理由必須 |
| inventory_policies | 工具全体で1件。安全在庫≦発注点≦目標 |
| supplier_items | 旧購買条件の保存専用。既存の一意制約を維持。工具単価未設定時の旧単価読み取り互換にだけ利用 |
| purchase_orders | 発注番号、依頼者、承認者、状態、注文確定日時 |
| purchase_order_items | 注文数・累計受入数、単価・型番・入数・納期のスナップショット |
| reorder_candidates | 工具単位の候補。OPENは工具につき最大1件 |
| audit_logs | 操作者、対象、JSON詳細。追記専用 |

全FKはRESTRICT削除。履歴と監査ログはUPDATE/DELETE拒否トリガーで保護。工具/操作者と旧設備×履歴時刻、注文状態×作成時刻に索引。訂正取引の元IDは一意として二重取消を防ぐ。

在庫は棚別、発注判定は工具全体の残高合算。on_orderはORDERED/PARTIALLY_RECEIVEDの注文数−受入数から集計予定。APPROVED/EXPORTEDは注文残に含めず、出力だけで注文確定しない。

CHECK制約: 在庫非負、引当≦実在庫、閾値順序、単価非負、入数正数、納期非負、注文数量正数、受入数0以上注文数以下、取引数量非ゼロ。部分一意索引とトリガーはSQL専用のため今後の差分生成時に維持する。

訂正理由、逆取引と原取引の工具/棚/数量の照合、注文状態遷移、権限、在庫と履歴の原子更新はPhase 2〜5のサーバー処理で保証する。納品受入の明細・注文ひも付け、取消残数、返品はPhase 5以降で再設計する。現在の入出庫APIは通常の入庫・出庫・取消を提供する。発注連携は未実装。

## Phase 2の追加

users.password_hash（nullable）とsessions、login_attemptsを追加。既存マイグレーションを変更せず20261103010000_authで追加。sessionsはトークンのSHA-256を主キーとし、ユーザーFK、作成/最終利用/絶対期限を保持。login_attemptsは社員IDのハッシュをキーとし、試行数と窓の開始日時を保持し、行ロックを伴うupsertで同時試行を制御する。ユーザーの無効化/降格/パスワード変更時にセッションを削除。ユーザー本体や業務履歴は削除しない。

管理変更と成功の監査ログは同一トランザクション。scryptのパラメータはN=32768/r=8/p=1、16バイトsalt、64バイト鍵。パスワード設定は12〜128文字。失効したセッションの定期削除は後続運用整備で追加する。

## Phase 3の利用方法

Phase 3当初は既存モデルと制約を利用した。現在は工具のdepartment/unit_price追加と2ロール化、出庫の設備必須CHECK解除の追加移行まで適用する。工具は方針と一緒に登録/更新し、コードは正規化後の一意制約で保証する。物理削除は提供しない。在庫行または取引履歴を持つ工具の数量単位は変更できない。

初期在庫は未登録のtool_id/location_id組にのみ登録する。reservedは必ず0。正数はRECEIVE履歴（理由「初期在庫登録」）を作成する。0の場合はCHECK制約に従い取引履歴を作らず、残高と監査のみ保存する。

audit_logsのINITIAL_STOCK_REGISTEREDイベントはentity_idをphase3-initial:<UUID>とし、detailsにtool_id/location_id/quantity/stock_balance_idを保持する。正数のinventory_transactions.idempotency_keyも同じ値を使用する。初期登録のロック区間内でこの監査を照合するため、0の登録も再送判定できる。異なる操作者・内容でのキー再利用は409となる。再送でも現在のセッションと権限を検証する。

設備・仕入先・購買条件の既存行、外部キー、一意制約は過去履歴を保つため残す。管理操作と初期シードからは除外する。単価はtools.unit_priceを優先し、NULLの場合だけ旧優先条件の価格で補う。仕入先情報を公開DTOには含めない。

## Phase 4の取引処理

追加移行20261107000000_simple_inventoryでinventory_transactions_validを更新し、ISSUEの設備必須条件だけを外す。行データは変更しない。既存の在庫CHECK、取引キー/逆取引元の一意制約、履歴/監査の更新削除禁止を維持する。

ISSUEは負数、RECEIVEは正数、REVERSALは元取引の逆符号。通常入出庫では理由不要。ADJUSTMENTは旧履歴としてのみ保持し、新規作成しない。旧ADJUSTMENTとREVERSALの理由必須制約を維持する。reservedをクライアントから変更せず、変更後on_handがreserved以上かつ0〜2147483647であることを確認する。棚別残高の条件付き更新にも確認時の値を指定する。

全操作でinventory_transactions.idempotency_keyはphase4:<UUID>。同じキーを同時に使う要求はスキーマ名とキーを使うトランザクションアドバイザリロックで順序付ける。成功時はINVENTORY_MUTATION監査を取引IDにひも付け、正規化した要求・順序を固定した要求フィンガープリント・確定前後の残高を保存する。再送は現在の権限・操作者と要求全体を照合して元の確定結果を返す。

逆取引の工具・棚・設備・数量は元履歴から取得する。二重取消はreverses_idの一意制約と工具行ロックで防ぎ、元履歴を変更しない。元マスタが無効でも逆取引を許可するが、既に消費済みの入庫の取消で在庫/引当条件を破ることはできない。取消の再取消とRETURNの取消は今回提供しない。

履歴の日付は日本時間の開始日00:00以上、終了日翌日00:00未満をUTCへ変換する。同時刻の履歴はID降順で安定化し、50件単位で返す。公開履歴DTOは工具/棚と社員ID・氏名・状態に限定し、設備、資格情報、単価は含まない。本人履歴は本人のISSUE/RECEIVEとそれらのREVERSALとする。
