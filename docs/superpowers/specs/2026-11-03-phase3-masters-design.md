# Phase 3 — 工具・在庫マスタ設計案

状態: 利用者が本設計に基づく実装・テストを承認済み。実装と全37件のテスト・型検査・本番ビルド・Prisma validate・PC/タブレット幅でのブラウザ検証が完了。レビュー指摘は回帰テストで修正・検証済み。

## 目的と受入条件

基準は `markdown/ToolStock_Manager_Codex_開発指示.md` の4章・5章・6章・9章のPhase 3。現場の利用者が工具番号・名称・型番から工具と棚別在庫を検索でき、管理者がマスタおよび初期在庫を登録できる状態にする。Phase 2の認証・セッションを維持し、現在の2ロール（WORKER / ADMIN）の権限を適用する。

- 工具、設備、保管場所、仕入先の一覧・登録・更新・有効/無効切り替えを提供する。
- 工具別の購買条件（仕入先、発注先型番、単価、発注単位、納期、優先仕入先）と在庫方針を管理する。
- 工具検索、工具詳細、保管場所別の実在庫・引当・出庫可能数を表示する。
- 工具×保管場所ごとの初期在庫を一度だけ登録できる。既存残高の上書き、重複コード、権限外の更新は拒否する。
- 初期在庫の残高・入庫履歴・監査は同じDBトランザクションで保存する。連打や再送で在庫を二重計上しない。

## 現状と制約

- Next.js 16.1.6 / React 19.2.4 / TypeScript 5.9.3 / Prisma 7.3.0 / PostgreSQL 17。既存の固定依存を使い、新規ライブラリは追加しない。
- Prismaには必要な全マスタ・残高・履歴・監査モデルが存在する。初期計画ではDDL追加や既存マイグレーション変更を行わない。
- 業務コードのユニーク制約、棚別残高の複合ユニーク制約、在庫非負・引当超過禁止・在庫閾値のCHECK制約、優先仕入先の部分一意索引、履歴の変更禁止トリガーを維持する。
- セッションはDBで検証する。操作者はセッションから取得し、リクエストの操作者IDを信用しない。
- 既存の `mutate`、Origin照合、入力サイズ制限、日本語エラー、JSONとHTMLフォームの応答方式を利用する。
- 数量は整数、単価はDecimal、時刻はUTC保存・Asia/Tokyo表示。金額はJSONでも小数文字列として扱う。
- ローカルの架空データだけを使う。秘密情報や資格情報を文書・ログ・Gitへ出さない。
- 既存開発DBのシードを再作成せず、既存残高・履歴を変更しない。検証は専用テストDBの一時スキーマで行う。

## 実装方式の検討

1. **既存構成を拡張する方式（提案）**: Server Components、通常のHTMLフォーム、Route Handlers、Prismaのサービス層を使う。認証・エラー応答・隔離DBテストを再利用でき、既存の運用に合わせられる。
2. クライアント中心の管理画面: 検索などの即時操作は作りやすいが、状態管理とAPI連携が増える。今回の一覧・検索・登録には不要で、導入しない。
3. 外部CMSや別バックエンド: マスタ画面を分離できるが、既存セッションと在庫トランザクションの統合や運用が増える。ローカル運用と既存の整合性保証に適さない。

今回の要件には1を採用するのが適切と判断した。技術構成の変更は行わず、既存ページと同じ日本語のフォーム・一覧・保存結果表示を拡張する。以下の具体仕様はCodexの提案であり、利用者が個別に指定した内容とは区別する。

## 対象画面と操作

| 画面 | 機能 | 閲覧・操作 |
| --- | --- | --- |
| `/tools` | 工具番号・名称・型番の部分一致検索、分類・有効状態の絞り込み、棚合計在庫、詳細リンク | 全ロール閲覧。初期表示は有効のみ |
| `/tools/new` | 工具基本情報と工具全体の在庫方針を一括登録 | `masters:write` |
| `/tools/[id]` | 基本情報、棚別実在庫・引当・出庫可能数、有効状態、在庫方針 | 全ロール閲覧 |
| `/tools/[id]/edit` | 工具基本情報、在庫方針の更新、有効/無効切り替え | `masters:write` |
| `/tools/[id]` 内の購買条件 | 条件一覧。権限のある利用者に登録・変更フォーム | 閲覧は `masters:write` または `orders:read`。更新は `masters:write` |
| `/tools/[id]` 内の初期在庫 | 未登録の保管場所を選び、初期数量を登録 | `masters:write` かつ `inventory:receive` |
| `/admin/masters` | 設備、保管場所、仕入先の一覧・登録・更新・有効/無効切り替え | `masters:write` |

管理者だけが工具詳細で購買条件を閲覧・編集できる。作業者向けのHTML・JSONには単価・仕入先購買条件を含めない。設備・保管場所の選択肢と在庫は両ロールから参照できる。

検索語は最大100文字、分類は最大64文字。検索は大文字小文字を区別せず、複数対象項目をORで検索し、分類・有効状態とはANDで組み合わせる。状態は有効・無効・すべて。未指定は有効のみ。不正な絞り込みは400相当の入力エラーを表示する。

一覧は1ページ50件、ページは1以上の整数。件数・前後移動・全件数を表示し、工具コード順の安定した並びにする。範囲外ページは空一覧と戻る導線を表示する。該当なし、未登録の棚、無効な工具・保管場所も区別する。無効なマスタの既存在庫や履歴は引き続き参照可能にする。

物理削除は提供しない。業務コードは登録後の画面から変更しない。APIでも更新時のコード変更は拒否する。名称・分類・メーカー・型番・単位・状態といった属性を更新できる。利用中の工具の単位変更は、在庫行または取引履歴が存在する場合は409で拒否し、別工具としての登録を案内する。設備や保管場所の名称変更は過去の取引数量へ影響させない。

Phase 4の出庫・入庫・調整・履歴検索、Phase 5の発注候補・承認・発注書出力、分析、CSV一括取込、外部送信は今回の対象外とする。工具詳細には現在の棚別残高を表示し、履歴検索画面は追加しない。

## 入力と業務ルール

### マスタ

- 工具・設備・保管場所・仕入先コードは前後空白を除き英字を大文字化し、`[A-Z0-9_-]{1,32}` に限定する。同じ種類内の重複は409とし、DBの一意制約でも保証する。他種類との同一コードは許可する。既存シードのコードを変換しない。
- 工具名・設備名・保管場所名・仕入先名は前後空白を除き1〜100文字、分類は1〜64文字、単位は1〜16文字。メーカー・型番は0〜100文字。現DBが非NULLのため任意項目の未入力は空文字列で保存する。
- メールは任意、最大254文字。入力時には基本的なメール形式を確認し、未入力はNULLにする。メール送信機能は追加しない。
- activeは明示的なbooleanとして検証する。フォームの `true` / `false` のみをbooleanへ変換し、それ以外の文字列を真として扱わない。
- APIは許可された項目だけを採用する。ID、操作者、在庫数、日時などをマスタの更新データへ展開しない。UUID・文字列型・長さをDB操作前に検証する。

### 在庫方針

工具全体で `0 <= safety_stock <= reorder_point <= target_stock <= 2147483647`。新規工具は全項目未指定の場合に限り0/0/0を初期値とする。既存シードの15/30などの値は維持する。新規工具と方針は同一トランザクションで作成し、更新も工具と同時保存する。

### 購買条件

- 工具×仕入先につき1件。新規登録の重複は409、更新は既存条件のIDを指定する。
- 単価は0以上、整数部12桁以内、小数部2桁以内の十進文字列。指数表記、負数、NaN、無限大、3桁以上の小数は拒否する。JavaScriptの浮動小数点への変換で金額を丸めない。
- 発注単位は1〜2147483647、納期日数は0〜2147483647の整数。フォームの数字文字列とJSONの整数を受け付け、小数・指数文字列・空文字列・booleanを拒否する。
- 発注先型番は任意で0〜100文字。未入力はNULL。
- 有効な工具・仕入先だけに購買条件を新規登録・更新できる。無効な条件は既存値の参照のみ許可する。仕入先の無効化では既存条件を削除しない。画面は無効な仕入先であることを明示する。
- 優先仕入先は工具につき最大1件。優先を切り替える操作では工具行をロックし、旧条件のpreferred解除と対象条件の保存を同一トランザクションで行う。部分一意索引を維持する。優先なしも許可する。
- 新規登録や更新で過去の発注明細のスナップショットを変更しない。

### 初期在庫

- 有効な工具と有効な保管場所に対してのみ、**その工具×保管場所にstock_balances行が存在しない場合**に登録できる。残高0の既存行も登録済みと扱う。
- 数量は0〜2147483647の整数。reservedはクライアントから受け取らず必ず0。quantity=0でもstock_balances行と監査を作成し、以後の初期登録を禁止する。0の入出庫履歴は禁止されているため、この場合は取引履歴を作らない。
- 正の数量はstock_balances、RECEIVEのinventory_transactions、audit_logsを同じトランザクションで作成する。履歴の理由は固定の「初期在庫登録」、actor_user_idはセッションから取得し、設備はNULLとする。
- 操作ごとにUUIDのリクエストキーをサーバーがフォームへ付与し、JSONではクライアントに必須指定させる。DBへは `phase3-initial:<UUID>` のidempotency_keyで保存する。
- 同じキー・同じ操作者・同じ工具・同じ棚・同じ数量の再送は成功済みの結果を返し、新たな書き込みをしない。同じキーで内容または操作者が異なる場合は409。
- 数量0には取引履歴がないため、初期在庫用の監査イベントのentity_idを上記キーにする。正の数量でも同じ監査形式を使い、detailsにtool_id/location_id/quantity/stock_balance_idを保存する。再送の検証はこの監査を正本にする。監査テーブルは追記専用であり、このイベントは更新しない。
- 新規テーブルは追加せず、初期登録ではマスタ書き込み共通のusersテーブルロックと認証の後、`LOCK TABLE stock_balances IN SHARE ROW EXCLUSIVE MODE` を取得して監査の再送照合を行う。同時のキー再利用・同じ棚への異なるキーの登録も一度しか成立しない。
- 処理順序は、入力の型・形式確認、usersテーブルロック、現在のセッション・権限検証、stock_balancesテーブルロック、監査による再送確認、対象の存在・有効状態確認、残高行存在確認、書き込みとする。利用者のロール・activeやマスタの状態は、この共通usersテーブルロックを使う全書き込み処理との間で安定させる。利用者行の共有ロックを認証より前に追加しない。
- 成功済みリクエストの同内容再送は、現在のセッション・必要な権限が有効であれば、登録後に対象工具・保管場所が無効化されていても元の成功結果を返す。新しい在庫の書き込みはない。現在のセッションが失効/無効なら401、権限を失っていれば403を返し、成功済み結果も公開しない。新しいキーでの登録は現在の対象状態を検証する。
- 登録済み残高の更新・上書きは409。別のキーでの再登録も409。既存の架空初期在庫はそのまま保持する。

## 構成とAPI

既存の `AuthService` とNext.js共通応答を再利用し、`src/lib/masters/` に入力検証、読み取り、マスタ書き込み、初期在庫書き込みを分離する。書き込みサービスは認証済み利用者のDTOだけを受け取って認可を省略する形にせず、セッショントークンを受けてDB内で認証・権限を検証する。

`AuthService` には既存の `asAdmin` を基に、要求権限とトランザクション内の操作を受け取る共通書き込み入口を追加する。まず `LOCK TABLE users IN SHARE ROW EXCLUSIVE MODE` を取得し、次に既存認証でセッションを更新・検証し、権限を確認して操作へ進む。ユーザー管理の `asAdmin` もこの入口を利用し、ロック順序を usersテーブル → sessions行 → 各業務テーブル に揃える。利用者行ロック → sessions更新の経路は追加しない。単独の読み取り認証はこれまでどおり短い処理で完了させる。

Phase 3は小規模なローカル運用なので、ユーザー管理・マスタ変更・初期在庫登録という低頻度の書き込みをこのusersテーブルロックで直列化する提案とする。閲覧は直列化しない。Phase 4で高頻度の出庫処理を追加する際は、別途ロック範囲と順序を見直す。ログイン・ログアウトの外部仕様は変えない。

| API | メソッドと用途 |
| --- | --- |
| `/api/tools` | GET 検索・一覧、POST 工具と方針を登録 |
| `/api/tools/[id]` | GET 工具詳細、POST 基本情報・状態・在庫方針を更新 |
| `/api/tools/[id]/supplier-items` | POST 購買条件の新規登録 |
| `/api/tools/[id]/supplier-items/[conditionId]` | POST 購買条件の更新 |
| `/api/tools/[id]/initial-stock` | POST 初期在庫登録 |
| `/api/masters/[kind]` | GET 一覧、POST 登録。kindはmachines/locations/suppliersの許可リスト |
| `/api/masters/[kind]/[id]` | POST 更新・有効/無効切り替え |

全GETで認証・必要な閲覧権限を確認し、`Cache-Control: no-store` とする。工具詳細と工具一覧のDTOを明示し、作業者へ単価を返さない。mastersの仕入先一覧はmasters:writeまたはorders:read、それ以外の一覧はinventory:readを要求する。すべての書き込みはOrigin照合・セッション・権限・入力検証を通す。未ログイン401、権限不足/Origin不一致403、不正入力400、未存在404、重複/状態競合409、入力過大413、不正Content-Type415、接続不能503。HTMLフォームは既存の303リダイレクト方式を使い、成功・失敗を日本語で表示する。各動的IDがUUIDでない場合は400とし、DBの内部エラーをそのまま返さない。

マスタの登録・変更・無効化、方針と購買条件の変更、初期在庫登録には監査イベントを同一トランザクションで作成する。before/afterは業務項目を明示して格納し、パスワード、セッション、生トークン、接続文字列を含めない。監査保存に失敗した場合は業務変更もロールバックする。
