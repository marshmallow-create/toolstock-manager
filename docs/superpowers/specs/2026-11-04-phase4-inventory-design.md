# Phase 4 — 入出庫・取消・履歴設計

2026-11-07の利用者指示を反映した現行仕様。変更計画は../plans/2026-11-07-simple-inventory.md。発注候補・承認・発注書・部分入荷・返品・CSVはPhase 5以降とする。

## 対象と権限

| 操作 | 権限と対象 |
| --- | --- |
| 在庫参照・出庫 | inventory:read / inventory:issue（両ロール） |
| 通常入庫 | inventory:receive（両ロール） |
| 本人の入出庫履歴 | history:own（両ロール。本人の入出庫を管理者が取り消した履歴を含む） |
| 全履歴 | history:all（管理者） |
| 理由付き全量取消 | inventory:reverse（管理者） |

通常入出庫の入力は工具・保管場所・数量だけ。理由付き手動入庫という別操作を設けず、理由入力は不要とする。通常取引のreasonは互換入力として任意で受理するが画面に入力欄を設けない。棚卸・設備・仕入先とその管理は廃止する。未認証者の入出庫は許可しない。

## 出庫と入庫

工具検索→工具選択→保管場所選択→数量（初期値1、＋/−、単位明示）→確定前後の見込み→確定。登録済みの有効棚が1つなら出庫時に自動選択する。操作者はセッションから取得する。

数量は1〜2147483647の整数。有効な工具・保管場所を使用する。出庫はavailable=on_hand-reservedまで、未登録棚の出庫は409。入庫は未登録の有効棚にも残高行を作成できる。変更後on_handがreserved以上かつ2147483647以下であることを確認する。reservedをクライアントから変更させない。発注明細にひも付く入庫入力は現在受け付けない。

新しい通常取引のmachine_idはNULL。新規の設備指定は400とする。ただし廃止前に成功した設備付き要求の同内容再送は、正規化済み要求フィンガープリントの一致を確認して元の結果を返す。旧履歴の設備参照はDBへ保持し、画面・履歴DTO・検索候補へは出さない。

## 取消

元履歴のID、1〜500文字の理由、UUIDのリクエストキーを指定する。管理者が元の数量を全量逆符号にして同じ工具・棚へ戻す。工具・棚・数量と旧設備IDは元履歴からサーバーが取得する。

ISSUE/RECEIVEと過去のADJUSTMENTを取り消せる。取消の再取消とRETURNの取消は提供しない。reverses_idの一意制約と工具ロックで二重取消を防ぐ。元マスタが無効でも取消は許可するが、入庫の取消で在庫不足・引当割れになる場合は拒否する。

元履歴を更新・削除せず、取消理由と操作者を追記する。UIは「理由を付けて取り消す（逆取引）」とする。正しい工具・棚・数量は取消後に新しい入出庫として登録する。取消と置換の一括編集は提供しない。

## 原子性・競合・再送

残高・取引履歴・INVENTORY_MUTATION監査を一つのDBトランザクションで保存する。AuthService.inventoryAuthorizedでusers共有ロック→セッション検証/更新→要求キーのトランザクションアドバイザリロック→工具行FOR UPDATE→棚別残高の条件付き更新の順序を固定する。

同じ工具の操作は順序付け、別工具は別セッションから並行処理できる。管理更新とのロック順序も共通化する。lock_timeoutは3秒、トランザクション上限10秒。競合・タイムアウトは全変更を戻して409と再試行案内を返す。

取引キーはphase4:<UUID>。同じキー・操作者・操作・正規化済み業務入力には元の確定結果を返す。異内容・異なる操作者のキー再利用は409。失敗した操作はキーを消費しない。成功済み再送でも現在の権限とセッションを検証する。

監査には正規化要求・キー順序を固定したフィンガープリント・確定前後の残高・確定結果を保存する。再送は保存結果を復元し、現在庫を確定時の残高として扱わない。成功後に対象マスタが無効になっていても、同内容再送を拒否しない。

## 履歴

/history と /api/historyは期間、工具、操作者、取引種別で検索する。50件単位、created_at降順・ID降順。YYYY-MM-DDの実在日を受け付け、日本時間の開始日00:00以上〜終了日翌日00:00未満をUTCへ変換する。不正日付・UUID・種別・ページは400。設備フィルターは設けず、非空のmachine_id検索入力は400とする。

history:allがない利用者は本人のISSUE/RECEIVEと、それらに対するREVERSALだけを閲覧できる。他人の操作者フィルターは403。他人の非公開履歴IDを直接指定した場合は404。管理者は全履歴を参照でき、無効な工具・棚・利用者も検索対象とする。

/history/[id] と /api/history/[id]は詳細・元履歴/逆取引へのリンク・取消理由・操作者・棚・符号付き数量・時刻を返す。工具詳細の直近5件にも同じ本人制約を適用する。DTOには必要な業務項目だけを選び、設備・資格情報・セッション・単価を含めない。historyOptionsはtools/actorsだけを返す。

InventoryResultはid/type/tool_id/location_id/actor_user_id/machine_id/quantity/on_hand_before/on_hand_after/reserved/reason/reverses_id/created_atを保持する。machine_idは旧確定結果・逆取引の互換用であり、新規通常取引ではNULL。HistoryItemは取引属性とtool/location/actorおよびreversal_idを返し、machineは含めない。

## 経路と廃止機能

ページは /tools/[id]、/history、/history/[id]。工具一覧から工具を選び、詳細内の入庫・出庫欄で操作する。独立した入出庫ページは廃止し404にする。POST APIは /api/inventory/issue、/api/inventory/receive、/api/inventory/reverse。確定成功は303で確定履歴へ遷移し、JSONには確定結果を返す。エラーでは工具選択を保持する。Origin照合、no-store、認証/認可、入力上限、Content-Type検証は既存方式を利用する。

/inventory/adjust と /api/inventory/adjustは削除して404。設備・仕入先・購買条件の旧APIも404。旧ADJUSTMENT履歴と関連DB行は保存し、新規棚卸は作らない。追加移行20261107000000_simple_inventoryで出庫の設備必須CHECKだけを外し、非ゼロ数量・符号・逆取引元・理由と残高の制約を維持する。適用済みSQLや行データは変更しない。

## 検証

- 両ロールの理由なし入庫・設備なし出庫、管理者だけの取消、本人入庫とその取消の閲覧制約。
- 同時出庫、同じ/異なるキーの競合、二重取消、成功済み再送、旧設備付き成功要求の再送、新規設備指定拒否。
- 在庫不足、引当、整数上限、未登録棚、無効マスタ、権限変更、監査失敗の全ロールバック。
- 旧API/画面404、設備フィルター拒否、DTOの最小化、UTC/日本時間境界、ページング。
- 追加移行前後で既存業務行・関連・履歴が保持され、設備NULLのISSUEが可能なこと。
- PC/タブレット幅で数量＋/−、棚自動選択、見込み、入出庫・本人履歴・取消をブラウザで確認する。未実行の検証を成功と記録しない。
