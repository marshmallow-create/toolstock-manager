# Phase 4 — 手動入出庫・棚卸訂正・履歴設計案

状態: 利用者が本設計に基づく実装・テストを承認済み。実装と全64件のテスト・型検査・本番ビルド・Prisma validate・PC/タブレット幅のブラウザ検証が完了。コードレビューに重大・重要な指摘なし。基準コミットは ed20a39（Phase3）。

## 目的・範囲

基準は markdown/ToolStock_Manager_Codex_開発指示.md の権限表、手動出庫フロー、在庫整合性・履歴追跡性、Phase 4受入条件。作業者が工具・保管場所・数量・設備を選んで出庫でき、在庫管理者と管理者が理由付き入庫・棚卸・逆取引を実行できるようにする。全操作で残高・履歴・監査を同じトランザクションに保存し、同時操作と通信再送で在庫を壊さない。

今回の対象は出庫、発注にひも付かない理由付き手動入庫、棚卸実棚数の反映、理由付き全量逆取引、履歴の閲覧・検索。発注候補の生成・承認・発注書・発注残と部分入荷・返品・CSVはPhase 5以降とする。元仕様の出庫手順には候補判定もあるが、フェーズ定義と既存のPhase 3文書に従って候補機能をPhase 5へ分ける。Phase 4の残高・履歴をその入力にできる構成にする。

新規依存を追加せず、Next.js 16.1.6 / React 19.2.4 / TypeScript 5.9.3 / Prisma 7.3.0 / PostgreSQL 17を維持する。既存開発DBと資格情報にはテストで変更を加えず、TEST_DATABASE_URLの一時スキーマで検証する。実データ・本番・外部送信は扱わない。

## 方式の比較と提案

- **工具単位の行ロック＋条件付き残高更新（提案）**: 工具行を共通のロック対象にし、同じ工具に対する入出庫・棚卸・逆取引を順序付ける。別工具は並行処理でき、棚別残高行が未作成の場合も扱える。既存DBと制約を再利用できる。
- 全入出庫の一括直列化: 既存のPhase 3管理用トランザクションをそのまま使えば構造は単純だが、別工具まで待たせる。通常出庫には採用しない。
- SERIALIZABLEと自動再試行: 成立するが、再試行と利用者向け結果の整理が増える。今回の単一工具・単一棚ごとの操作には必要ない。

既存のHTMLフォーム・Route Handlers・サービス層を拡張する。数量の＋／−と変更後見込みの表示だけに小さなクライアントコンポーネントを使う。以下はCodexの具体的な提案であり、個別指定された仕様とは区別する。

## 権限

| 操作 | 許可する権限・ロール |
| --- | --- |
| 工具・棚在庫の参照 | inventory:read（全ロール） |
| 出庫 | inventory:issue（作業者、在庫管理者、管理者） |
| 理由付き手動入庫 | inventory:receive と inventory:adjust（在庫管理者、管理者） |
| 棚卸実棚数の反映・逆取引 | inventory:adjust（在庫管理者、管理者） |
| 本人の出庫履歴 | history:own（全ロール。出庫操作がない購買担当は通常空） |
| 全員の入出庫履歴 | history:all（在庫管理者、購買担当、管理者） |

操作者は毎回DBセッションから確定し、入力されたactor_user_idは採用しない。画面のボタンだけでなく、APIとサービスで権限を検証する。再送でも現在のセッション・権限を検証し、失効は401、権限喪失は403とする。

## 操作仕様

### 出庫

- 工具検索→工具選択→保管場所選択→数量（初期値1、＋／−、単位明示）→設備選択→出庫前/後見込み→確定。
- 有効な工具・保管場所・設備だけを使用する。工具の登録済みかつ有効な棚が1か所なら自動選択する。設備は本人の明示選択とし、端末に前回値を保存しない。
- 数量は1〜2147483647の整数。設備は必須。棚別残高のavailable=on_hand-reserved以上には出庫できない。残高がない棚は在庫不足として409。
- サーバーがロック内で最新残高を読み直し、on_handを数量分減らす。reservedを変更せず、quantityが負のISSUE履歴を保存する。
- 画面の見込みは参考値とし、確定時のサーバー判断を優先する。既に他人が出庫して不足した場合は409と日本語の再確認案内を返す。

### 理由付き手動入庫

- 有効な工具と有効な保管場所、1〜2147483647の整数、1〜500文字の理由を必須とする。
- 登録済み棚はon_handを加算する。未登録の工具×棚はreserved=0の残高行を作成し、同時に正数のRECEIVE履歴を保存する。
- 加算後のon_handが2147483647を超える場合は409。reservedの入力は採用しない。
- 発注書とのひも付けや発注残の消し込みはまだ行わない。order_id/order_item_idなど発注ひも付けを意味する入力があれば400で拒否する。画面は「理由付き手動入庫」と明記する。

### 棚卸

- 登録済みの有効な工具×有効な棚について、実棚数（0〜2147483647）、表示時のexpected_on_handとexpected_reserved、理由1〜500文字を受け取る。
- ロック後の現在値が表示時の数量/引当と一致しなければ409として再読込を求め、現在庫を上書きしない。
- 実棚数がreservedを下回れば409。差分=実棚数-current_on_handをADJUSTMENTとして記録し、on_handを実棚数へ変更する。
- 差分0は「数量変更がありません」と409を返し、非ゼロ履歴の制約を守る。未登録棚の開始には初期在庫登録または手動入庫を案内する。
- この方式は提出時の残高との差異を検出する。作業中の物理的な入出庫を停止する棚卸業務フローや、在庫が一度変動して同じ値に戻った経路の検出までは扱わない。

### 訂正（逆取引）

- 元履歴のID、理由1〜500文字、リクエストキーを指定し、元の数量を全量逆符号にして同じ工具・棚へ反映する。工具・棚・数量・元設備はサーバーが元履歴から取得する。
- 取り消せる元履歴はISSUE、RECEIVE、ADJUSTMENT。Phase 3の正数初期在庫RECEIVEも対象。REVERSALの再取消、RETURN、既に逆取引のある履歴は409。
- 元履歴を変更・削除しない。REVERSALのreverses_idで元履歴に関連付け、元履歴と逆取引の双方を閲覧できる。逆取引のactor_user_idは訂正を実行した人。
- 現在のon_handへ逆数量を加え、0〜2147483647かつreserved以上になる場合だけ成立する。既に使用済みの入庫を取り消して負在庫にすることはできない。
- 過去の誤操作を戻せるように、元の工具・棚・設備が後から無効化されても逆取引は許可する。
- UIは「理由を付けて取り消す（逆取引）」とする。正しい数量・設備・別工具への変更は、取消後に新規の入出庫として登録する。取消と置き換えの一括編集は今回提供しない。数量を直接編集する画面は作らない。

## 再送・DB整合性

全操作はUUIDのrequest_keyを必須にする。フォームにはサーバーが発行したキーをhiddenで渡す。Phase 4の全操作で名前空間を共有し、DBのidempotency_keyはphase4:<UUID>とする。

現在の認証・認可の後にキーのトランザクションアドバイザリロックを取得し、成功済み記録を照合する。同じキー・同じ操作者・同じ操作・同じ正規化済み業務入力は元の結果を返し、残高・履歴・監査を増やさない。数量・設備・工具・棚・理由・棚卸の期待値・取消元などが異なる再利用は409。失敗した操作はキーを消費しない。

成功結果には取引ID、工具・棚・種別・数量、確定前後のon_hand、reserved、操作者、設備、理由、関連元、確定時刻を含める。監査にはこの結果と正規化した要求内容を保存し、再送で元の確定結果を復元する。再送時点の現在庫とは区別し、画面では履歴と最新残高の両方へ移動できるようにする。成功後に対象マスタが無効になっていても、現在の権限が有効な同内容再送は元の結果を返す。

### ロック順序

1. usersテーブルのSHAREロックを取得する。Phase 4同士は共存でき、既存Phase 3のSHARE ROW EXCLUSIVEによるユーザー/マスタ/初期在庫変更とは順序付ける。
2. セッションを検証/更新し、必要な権限を確認する。既存の管理用authorizedは動作を維持し、在庫用の認可付きトランザクション入口を追加する。呼び出し元の入力からロックモードを選ばせない。
3. request_keyに対応するトランザクションアドバイザリロックを取得する。DB/スキーマとPhase 4の名前空間を含む文字列をハッシュして使用し、任意SQLは構築しない。
4. 成功済みキーを照合し、再送なら結果を返す。新規取消の場合は不変の元履歴から工具IDを取得する。
5. 対象工具行をFOR UPDATEでロックする。対象の有効状態、取消済み状態、棚残高をこの後に再検証する。
6. 対象棚の残高を更新/作成する。条件付き更新と既存のCHECK・ユニーク制約も利用し、残高・履歴・監査を同時コミットする。

Phase 4ではstock_balances全体をロックしない。同じ工具は棚が違っても順序付けし、別工具は別セッションの利用者で並行実行できる。同じ利用者の同じセッションではセッション更新による待ちが生じうる。処理中にusersの共有ロックを管理用へ格上げしたり、管理用トランザクションを入れ子で呼んだりしない。

既存のinventory_transactions.idempotency_keyとreverses_idの一意制約、残高のCHECK、履歴・監査の追記専用トリガーを維持する。既存モデルで足りるため、初期提案ではDDL変更なし。履歴検索で必要なインデックス追加が実測で必要になれば追加マイグレーションとして扱い、既存DDLを書き換えない。

ロック設計の根拠: [PostgreSQL 17 Explicit Locking](https://www.postgresql.org/docs/17/explicit-locking.html)。共有ロックの互換性・一貫した取得順序・トランザクションアドバイザリロックの解放規則を確認した。

## 履歴・検索

/historyと/api/historyを提供し、期間、工具、設備、操作者、取引種別で絞り込む。50件単位、created_at降順・ID降順とし、件数・ページ移動を表示する。日付入力はYYYY-MM-DDの実在日だけを受け付け、日本時間の開始日00:00以上〜終了日の翌日00:00未満をUTCへ変換する。開始日>終了日、不正UUID、不正種別、不正ページは400。

history:allがない利用者は、自分が操作者のISSUEと、それらを取り消したREVERSALだけを閲覧できる。逆取引が管理者による操作でも、自分の出庫の取消結果は確認できる。他人の操作者フィルターは403。history:allがある利用者は全取引を参照でき、無効化済みの利用者・工具・設備・棚も検索対象に含める。

/history/[id]と/api/history/[id]は履歴詳細、元履歴/逆取引へのリンク、取消理由、操作者、設備、棚、符号付き数量、時刻を表示する。他人の履歴IDを直接指定した非許可利用者には404。履歴DTOと検索候補には社員ID・氏名等の必要項目だけを選び、password_hashやセッション、購買単価を含めない。

工具詳細には現在の権限で見える直近5件と履歴検索への導線を追加する。作業者向けの直近履歴も同じ本人制約を必ず適用する。元履歴の設備フィルターで、その取消も確認できるようにREVERSALへ元設備を引き継ぐ。過去の表示名は現在のマスタ名を参照し、無効なマスタには無効表示を付ける。

## 画面・APIと応答

| 画面 | API | 操作 |
| --- | --- | --- |
| /inventory/issue | POST /api/inventory/issue | 手動出庫 |
| /inventory/receive | POST /api/inventory/receive | 理由付き手動入庫 |
| /inventory/adjust | POST /api/inventory/adjust | 実棚数を反映 |
| /history | GET /api/history | 履歴検索 |
| /history/[id] | GET /api/history/[id] | 履歴詳細 |
| 履歴詳細の取消フォーム | POST /api/inventory/reverse | 理由付き逆取引 |

各入力画面には工具検索と選択、棚の選択、現在庫、必要入力と数量単位、日本語のエラー/成功表示、戻る導線を用意する。工具詳細とダッシュボードから権限に応じた導線を追加する。工具の事前選択はtool_idのGETパラメーターで行い、サーバーで検証する。未存在/不正な事前選択は404。

GETと成功結果はno-store、書き込みは既存のOrigin照合・入力サイズ制限・型検証を使う。JSONは初回/再送とも200で結果を返す。HTMLフォームは303で確定した履歴詳細へ移動する。入力エラーの戻り先URLはURLSearchParamsで組み立て、工具の事前選択とエラーを正しく保持する。既存の成功時リダイレクト固定関数を必要最小限で拡張し、既存認証・マスタフォームの挙動を維持する。

未ログイン401、権限不足/Origin不一致403、入力不正400、未存在404、在庫不足/競合/重複取消409、入力過大413、不正Content-Type415、DB接続不能503。内部SQLや接続情報を返さない。ロック待ちは有限にし、タイムアウトは在庫を書き換えず再試行案内を返す。同じキーによる安全な再送を案内する。
