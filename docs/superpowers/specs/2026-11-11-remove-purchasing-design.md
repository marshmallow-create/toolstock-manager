# 発注業務の廃止とDB整理

## 目的・確定した範囲

このシステムから発注先・仕入先への発注業務は行わず、注文ワークフローを廃止する。利用者が選択した範囲は「発注ライン・発注数は残し、仕入先・注文・発注済み集計を削除する」。

## 検討した方法

- 発注ライン・発注数を残して注文構造を削除する（利用者が選択）。外部で行う発注のための在庫管理項目を維持できる。
- 発注ライン・発注数も削除する。DBをさらに減らせるが、利用者が必要とする管理項目がなくなるため採用しない。
- 画面だけ非表示にする。不要な仕入先・注文テーブルが残り、DB整理の目的を満たさないため採用しない。

## 変更内容

| 対象 | 変更 |
| --- | --- |
| suppliers / purchase_orders / purchase_order_items | データを監査ログへ退避してから3テーブルを削除 |
| OrderStatus | 注文テーブル削除後に型を削除 |
| Prismaモデル | Supplier / PurchaseOrder / PurchaseOrderItem と User / Tool の関連定義を削除 |
| 工具一覧・詳細API | 注文明細の参照・集計と on_order プロパティを削除 |
| 工具一覧・登録画面 | 「発注済み」列・表示・自動集計の説明を削除 |
| 発注ライン・発注数 | 入力・表示・Excel取込・変更履歴を維持 |
| 現行文書・テスト | 発注業務の廃止と残す項目に合わせて更新 |

画面・APIから消すのは「発注済み」であり、0固定の代替値は返さない。発注数は現在と同じく OPEN 発注候補の数量を保持する。注文を扱う画面・APIは現在未実装のため、新たな廃止画面は作らない。

## データ移行と保護

以下は実装側の提案であり、既存の旧構造整理と同じ方式に合わせる。

- 適用済み移行を変更せず、追加マイグレーションを作成する。
- 1トランザクションで退避と削除を行う。対象表をロックし、退避したデータと削除対象のずれを防ぐ。
- データがある場合は、全行・全列をJSONとして audit_logs の専用イベント `PURCHASING_SCHEMA_ARCHIVED` に保存する。既存監査イベントは変更しない。
- 監査の操作者を既存ユーザーから選べない場合は、データがある移行を中止し、対象表を保持する。空DBへの適用は可能とする。
- 注文明細、注文、仕入先の順で削除し、CASCADEで対象外の構造を削除しない。
- 通常利用DBへの適用前に既存のバックアップスクリプトでDB全体を退避し、移行前後の在庫・履歴・ユーザー・発注ライン・発注数を照合する。
- 削除後の旧注文データは業務APIからは参照せず、監査ログとバックアップに保持する。復旧にはバックアップまたは個別復元作業が必要。

## 維持するもの・対象外

工具、棚番、単価、在庫、入出庫・取消、認証、ユーザー、監査を維持する。発注ラインの inventory_policies、発注数の reorder_candidates、CandidateStatus は保持する。発注候補の工具列への移設、状態型の縮小、引当や安全在庫などの追加整理は今回行わない。

作業開始時から工具一括変更・金額表示などの未コミット変更が存在するため、その内容を保持して今回の変更を重ねる。既存変更を取り消したり、まとめてコミットしたりしない。

## 検証・完了条件

- 追加移行を専用テストDBで検証し、非空・空DBでの適用、退避内容、退避失敗時のロールバック、対象表・注文型の削除を確認する。
- 在庫・履歴・資格情報・発注ライン・発注数・既存監査が維持されることを確認する。
- 工具一覧・詳細APIが注文構造に依存せず、画面に「発注済み」がなく、発注ライン・発注数の登録・変更・Excel取込が機能することを確認する。
- Prisma検証・型チェック・関連テスト・本番ビルドを実行する。
- 通常利用DBへの適用状況とバックアップ先を、コード変更の検証結果と分けて報告する。
