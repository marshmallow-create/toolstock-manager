# 要件（2026-11-07更新）

## 全ページの共通レイアウト

マイページ・履歴一覧/詳細・工具詳細/登録/編集・ユーザー管理・ログイン・404画面は、共通のWorkspaceShellを利用する。最大幅1600px、左右余白16px（md以上24px）、上下余白20px、ページ見出し24px、本文/入力欄14px、カード余白12pxを基本とする。認証済みの画面には本人のログイン情報とログアウトを表示し、メニューは権限と画面の導線に従う。未ログイン画面には認証済みユーザー向けの操作を表示しない。各画面の戻るリンク、業務処理、サーバー側の認証・認可を維持する。

## 入出庫履歴の表示と単価検索

- 履歴とマイページは共通のヘッダー・ログイン情報・メニュー・最大幅1600px・余白・文字サイズを利用する。
- 列は右から「日時・品目コード・品目名・カテゴリー・入出庫履歴・数量・操作者・在庫数・単価」の順。日時は日本時間。
- 入出庫履歴欄は増減に応じて「入庫」「出庫」を表示し、数量は当該取引数量の絶対値。取消を含め、詳細画面では元の種別と理由を確認できる。
- 在庫数は当該在庫記録の取引直後の残高。新規取引は在庫数・単価を記録し、工具単価を変更しても過去の単価は変えない。取消の単価は元取引の値を引き継ぐ。
- 既存履歴は書き換えない。旧在庫数は対応する監査記録で確認できる場合だけ補い、確認できない値と旧単価は「—」とする。
- 単価は下限・上限を独立指定でき、両端を含める。空欄は条件なし。下限が上限を超える指定・負数・小数3桁以上・指数表記を拒否し、未知の単価は範囲検索に含めない。
- 単価の閲覧・範囲検索は既存の管理者権限を維持する。作業者のAPI/HTMLには単価値を含めず、範囲検索による推測も拒否する。

## 利用者と開始画面

最初に / を開くと /login へ移動する。社員IDとパスワードで認証し、ログイン後はマイページ（/dashboard）のログイン情報下で工具一覧を検索し、ログアウト左のメニューから履歴・管理操作へ進む。入出庫は一覧で工具を選び、工具詳細の入庫・出庫欄を開いて操作する。ロールは作業者（WORKER）と管理者（ADMIN）の2種類だけ。

両ロールが在庫参照・入庫・出庫・本人の入出庫履歴を利用できる。管理者だけが工具・保管場所・単価・初期在庫・ユーザーを管理し、全履歴を閲覧できる。取消は理由を付けた全量逆取引として管理者が行う。

## 工具・保管場所

工具番号・名称・型番の部分一致、分類・有効状態で検索し、50件単位で表示する。工具詳細には棚別の実在庫・引当・出庫可能数と在庫方針を表示する。登録時の部門・単価・在庫数・棚番号・発注点・発注数等の入力は既存仕様を維持する。

単価の正本はtools.unit_price。未設定の旧工具だけ旧優先条件の単価を読み取り互換で補う。単価は管理者だけに表示し、仕入先情報は公開DTOへ含めない。棚番はtools.shelf_codeに保持し、工具登録・編集から変更する。保管場所管理画面・管理API・メニューは廃止する。棚番の変更によって在庫数や過去の入出庫履歴は変更しない。

初期在庫は未登録の工具×棚へ一度だけ登録でき、0も登録済みとする。正数は入庫履歴、0/正数ともに監査を同一トランザクションで保存する。再送で再計上せず、別キーでの再登録も拒否する。

## 入出庫・履歴

通常の入庫・出庫は工具・保管場所・数量だけで確定する。通常入庫の理由は不要で、理由付き手動入庫という別操作は設けない。出庫では実在庫から引当を除いた数量を超えられない。入庫は未登録棚にも登録できる。

履歴は期間（日本時間）、工具、操作者、種別で検索する。作業者は本人のISSUE/RECEIVEと、それらを管理者が取り消したREVERSALだけを閲覧できる。管理者は全履歴を参照できる。工具詳細の直近履歴と履歴ID直接指定にも同じ制約を適用する。

取消は元履歴を変更せず、理由と訂正者を逆取引に追記する。正しい内容は新しい入出庫として登録する。同じUUID・同じ操作者・同じ正規化済み入力の再送では元の確定結果を返し、在庫を二重計上しない。

## 廃止した機能とデータ保持

棚卸、設備、仕入先、購買条件の画面・登録・更新APIは提供しない。/inventory/adjust と /api/inventory/adjust、設備/仕入先マスタAPI、工具のsupplier-items APIは404となる。設備の入力・履歴表示・検索フィルターも廃止する。

既存の関連DBモデル・行・外部キー・旧ADJUSTMENT履歴は削除しない。旧履歴の取消と成功済み設備付き要求の同内容再送は維持する。新しい通常取引のmachine_idはNULLとし、新規の設備指定要求は拒否する。初期シードは設備・仕入先・購買条件を作成しない。

## 整合性と検証

整数数量、非負在庫、引当超過禁止、整数上限、コード一意、履歴追記型、UTC保存、認可・Origin照合を維持する。在庫・履歴・監査は原子的に更新し、同時出庫・二重取消・再送・権限変更・監査失敗を専用DBで検証する。既存の移行SQLを書き換えず追加移行で出庫の設備必須制約を外す。

発注候補・承認・出力・部分入荷・返品はPhase 5以降。仕入先管理の廃止を踏まえた発注先の扱いは、そのフェーズで再設計する。現在の入庫APIは発注明細にひも付く入力を受け付けない。
